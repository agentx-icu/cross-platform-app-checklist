# Technical release gates and data reliability

[简体中文](release-reliability.zh-CN.md)

Use this guide for first public releases, subsequent updates, and releases that change storage formats, data paths, credentials or native backends. Qualify the first artifact and preserve a populated baseline for future upgrades. Scope the work to the OS, architecture, channel and package formats actually shipped. Each gate maps to existing checklist IDs. See the [store guide](stores.md) for submission and channel requirements.

## Define the data contract before shipping

For each persistent store, record its owner (global, account, guest or device), source of truth, path and keys, format version, commit guarantee, retention and deletion rules, and backup and transfer policy. Account for identity keys, offline user content, pending operations and referenced media individually. State which uncommitted edits can be lost and when.

| Data class | Behavior to define |
|---|---|
| Identity and credentials | Stable local identity, encrypted profile, account pointer and key references. Define device-bound credentials, portable identities and server sessions, including logout, deletion, password changes and device transfer. |
| User content and operations | Define retention for history, drafts, attachments, training, recordings, pending and failed operations. Give references and operations stable IDs and define upgrade, restore, deletion and retry behavior. |
| Preferences, cache and temporary state | Identify account and device preferences and which caches can be rebuilt. Keep user-created content, referenced files and pending operations in durable storage. |

Identify the supported historical versions. Inventory TestFlight builds, test-track builds and direct downloads already in use. Use real older artifacts to test every supported update or import path. If the first release has no supported predecessor, record the reason the historical upgrade case is inapplicable. Test clean install, cold reopen with populated data and the same-version recovery paths the product supports. Keep the installable candidate, populated synthetic profile and data format versions as the baseline for the first update. A higher-build test artifact through the same delivery path can exercise replacement installation. Record its coverage as installation mechanics and qualify data migration when a supported cross-version path exists. Retain reusable synthetic or sanitized fixtures for supported releases and backup formats.

Define the promise and test each direction independently. Cover new apps reading old data, old apps handling newer data, importing older backups, and interoperability between app versions. Include preference keys, key references and stable business identifiers that must survive an upgrade.

## Technical release gates

| Gate | Expected result | Checklist IDs |
|---|---|---|
| Offline cold start and unlock | Users can read and edit saved local data after an offline restart. Unlock the local identity under the product's authentication policy. Show a locked or retry state if credentials are temporarily unavailable, and use the defined recovery or reauthentication path if a key is missing. | [B3](lifecycle.md#b3-process-death-and-cold-start--p1), [P5](permissions.md#p5-data-at-rest-and-backup--p1) |
| Account isolation and key lifecycle | Scope private keys, history, queues, media and preferences by stable identity. Account selection and actual storage agree after switching, logging out, deleting, changing passwords or a failed import. Revoke writes by retired sessions and timers. Keep device credentials in secure storage or encrypt them with an OS-protected key. | [B5](lifecycle.md#b5-single-instance-and-multiple-windows--p1), [P5](permissions.md#p5-data-at-rest-and-backup--p1) |
| Writes and process interruption | Data reported as saved meets the commit contract and survives restart. Checkpoint during use and flush critical writes before backgrounding or orderly exit. Exercise low disk, read-only paths, I/O errors and process termination. Verify that a complete old or new state is readable and document the loss window for edits still being saved. | [B2](lifecycle.md#b2-persist-before-suspension--p0), [X7](testing.md#x7-interrupted-flows-and-access-changes--p0-for-stateful--permissioned-flows) |
| Older data and skip upgrades | Version database schemas, file layouts, preference keys, credentials and backups. Validate the source, serialize writers, and commit data and versions with a transaction or recoverable journal. Validate the new store before cleaning up the old store. Repeated launches and retries yield the same result. Verify business data, ownership and file references. | [B7](lifecycle.md#b7-local-data-migrations--p0) |
| Future formats and recovery | Preserve unsupported newer data and show an update requirement, or use a verified compatibility mode. Check versions for primary and recovery copies, merges and delayed writes. Distinguish a failed migration, corruption, denied access and a missing key. Preserve recoverable data. | [B7](lifecycle.md#b7-local-data-migrations--p0), [X7](testing.md#x7-interrupted-flows-and-access-changes--p0-for-stateful--permissioned-flows) |
| Backup, import and device transfer | Exercise app exports, cloud restore, device-to-device transfer and reinstall separately. Define backup coverage for identity, history, queues, media, preferences and keys. Snapshot related stores consistently. Validate format, integrity, size and paths before staging and committing an import. Test wrong passwords, truncation, tampering, low disk and partial restore. The original store remains usable after a failed restore. | [P5](permissions.md#p5-data-at-rest-and-backup--p1), [B7](lifecycle.md#b7-local-data-migrations--p0) |
| Network and delivery reliability | For networked apps, resume pending operations after restart. Reuse operation IDs on retry and deduplicate on the receiver where the protocol supports it. Distinguish queued, sent, delivered and read. Check stale operations, duplicates and conflicts after restoring an older backup. Use real peers to test poor connectivity, offline recovery, network changes, unavailable bootstrap or backend services, and version interoperability. | [B6](lifecycle.md#b6-durable-transfers-and-retry-ownership--p1), [B8](lifecycle.md#b8-offline-state-and-sync-conflicts--p1), [X8](testing.md#x8-network-environments--p1-for-networked-apps) |
| Installed artifact and degraded operation | Install the distributed package and run as a standard user. Cover the minimum supported and current stable OS in the support matrix. Verify actual loading of the app, runtime, plugins and native libraries. Check storage, credentials and first launch after an update. Exercise permission grant and denial for shipped core features, and measure cold start, migration duration and temporary disk usage. | [X1](testing.md#x1-device-matrix--p0), [X6](testing.md#x6-packaged-release-verification--p0-for-release), [P3](permissions.md#p3-degraded-paths--p1), [F2](performance.md#f2-app-size-and-startup-budgets--p1) |
| Diagnostics and containment | Retain artifact hashes, build identifiers and matching symbols. Record the migration version, failing phase and error category in diagnostics that omit keys, passwords, messages and recordings. Set rollout stop conditions and a forward-fix path. Users who already installed an update still need readable data or a fix. Offer binary rollback only after verifying both binary and data downgrade. | [X6](testing.md#x6-packaged-release-verification--p0-for-release), [X9](testing.md#x9-production-diagnostics--p1-for-released-apps) |

For SQLite, use the Online Backup API or another supported method to capture a consistent snapshot. Committed pages can still be in the WAL. Configure and test Android cloud and device-to-device transfer separately. Device-bound Apple Keychain items can be absent after transfer, so check that any restored ciphertext has a usable key. [SQLite Backup API](https://www.sqlite.org/backup.html), [SQLite WAL](https://www.sqlite.org/wal.html), [Android Auto Backup](https://developer.android.com/identity/data/autobackup), [Apple Keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility)

## First-release failure paths

Run the applicable cases through the product's actual entry points. Inject failure at the storage or transport boundary and use a fresh process where restart matters.

| Scenario | Acceptance assertion |
|---|---|
| Primary store temporarily unreadable ([B2](lifecycle.md#b2-persist-before-suspension--p0), [B7](lifecycle.md#b7-local-data-migrations--p0)) | Deny access or inject an I/O error while a stale recovery copy remains readable. Preserve both copies, report that opening can be retried and block writes from fallback or empty state. Once access returns, reopen the current data. Exercise missing, corrupt and unsupported-format stores separately under their own recovery rules. |
| Orderly exit or action fails to commit ([B2](lifecycle.md#b2-persist-before-suspension--p0), [X7](testing.md#x7-interrupted-flows-and-access-changes--p0-for-stateful--permissioned-flows)) | Deny the write on a normal save, logout, account switch or close. Keep unsaved work available for retry and advance the visible saved or active state only after commit. Track remote delivery separately if a send can succeed despite local history failing to save. Preserve the existing account pointer until the critical save succeeds. For imports that change linked files and metadata, fail after the first replacement and verify the original files, references and selection still agree. |
| Identity or guest data removed mid-operation ([B5](lifecycle.md#b5-single-instance-and-multiple-windows--p1), [B7](lifecycle.md#b7-local-data-migrations--p0)) | Define when removal takes effect. Test before that point, then terminate the process after the old data is isolated and before physical cleanup. A fresh process resumes cleanup, old writers and recovery copies cannot reattach the removed data, and a new or different identity sees only its own data. Force a recovery-copy read after resetting preferences and check that cleared settings stay cleared. Test an inaccessible storage lock separately from a confirmed live owner and verify a recoverable startup state for the former. |
| Partial same-version restore ([P5](permissions.md#p5-data-at-rest-and-backup--p1), [B7](lifecycle.md#b7-local-data-migrations--p0)) | Restore the account record, history, settings and queue with the identity file or device-bound key absent. Keep the surviving data usable under the recovery policy. If a portable identity can repair it, verify the full stable identity and authenticate the source. A matching import repairs missing material and preserves data and local account protection. Exercise a mismatch, wrong password, existing healthy identity and failure writing preferences or a recovery copy. Restored queues remain paused for review or explicit authorization before network dispatch. |
| Cancelled or uncertain delivery ([B6](lifecycle.md#b6-durable-transfers-and-retry-ownership--p1), [B8](lifecycle.md#b8-offline-state-and-sync-conflicts--p1)) | An accepted send request or progress event leaves the item pending with its owned source. Persist cancellation before confirming delete or clear. Restart before acknowledgement and after peer completion but before local settlement, then deliver a callback from the old attempt. Preserve the committed cancellation and apply completion only to the matching attempt. To preserve at-most-once delivery, retry automatically only when the previous attempt is known to have had no effect or the receiver deduplicates the operation. Leave uncertain non-idempotent actions pending for confirmation unless the product explicitly permits replay. Where replay is permitted, document and verify the replay boundary and user-visible state. |
| First-use consent, backup and playback ([P5](permissions.md#p5-data-at-rest-and-backup--p1), [M1](media-devices.md#m1-audio-session-and-focus--p0-for-apps-that-play-or-record)) | When applicable, interrupt creation after writing an identity profile but before writing its account record. On restart, recover the complete shareable identity. Reopen during required backup onboarding and reconnect before any required consent. Check that each gate still applies and that an unknown system share outcome leaves backup completion unconfirmed. Where scoring or progress depends on listening, fail the audio start or output. Keep progress unchanged, provide retry and require the relevant playback completion event. |

Where iOS backup policy excludes certain files, establish the exclusion on their destination or dedicated staging directory before writing sensitive material. Inject a failure setting the exclusion, then verify no excluded data lands in a backup-eligible path. Recheck after replacement and run an actual system backup and restore. For large exports and staging, measure peak memory and temporary disk use and check that interrupted imports or cancelled transfers reclaim unreferenced copies while referenced media stays readable. [Apple backup exclusion](https://developer.apple.com/documentation/foundation/optimizing-your-app-s-data-for-icloud-backup)

## Release promotion and delivered package

- **Draft release.** Where the channel supports staging, bind the candidate version and resolved tag commit to the reviewed source and a manifest of required assets and digests. Record the remote draft ID. For GitHub Releases, resolve the draft through an authenticated draft-aware lookup and use the numeric release ID for metadata and asset checks. The REST lookup by tag is for published releases. Test interrupted upload and retry, a missing required asset, an unexpected or wrong-digest asset, a mismatched tag or commit, and a draft that has already become public. Retry only with a matching draft and assets. Keep it private until the required inventory and checks pass, and leave published releases unchanged during staging. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name), [release assets API](https://docs.github.com/en/rest/releases/assets#list-release-assets)
- **Android native delivery.** Where 16 KB compatibility applies, inspect ELF alignment for every shipped native library, including compressed libraries. Verify the ZIP alignment of uncompressed libraries in both direct-download APKs and APKs generated by the distribution channel. For an AAB with uncompressed libraries, inspect the exact bundle with a versioned `bundletool` and require `PAGE_ALIGNMENT_16K`. Record the tool version, bundle digest and results from a passing 16 KB fixture and a rejected 4 KB fixture. For either packaging mode, install through the intended channel on a 16 KB system (for Play, use the intended test track), record the measured page size, disable compatibility fallback where available and invoke the native features. [Android 16 KB validation](https://developer.android.com/guide/practices/page-sizes)

Record source regressions, simulated failures or peers, CI provider execution, and runtime tests on the channel-delivered build with their own evidence. Keep real two-peer delivery, Apple system restore, physical audio and other hardware-dependent cases outstanding until exercised where applicable. [X6](testing.md#x6-packaged-release-verification--p0-for-release), [X7](testing.md#x7-interrupted-flows-and-access-changes--p0-for-stateful--permissioned-flows), [X8](testing.md#x8-network-environments--p1-for-networked-apps)

## Minimum acceptance matrix

Use a populated profile on each applicable platform and delivery path. For a supported upgrade, generate it with the older build. Include distinct values that make ownership, references and state observable, such as two identities, history and drafts, read and unread messages, pending and failed operations, attachments or recordings, and non-default settings. Include a large store or slow storage. Record process termination and device power-loss results separately.

| Scenario | Acceptance assertion |
|---|---|
| Clean install, then offline launch | Core offline features and local preferences work. Network failures and denied permissions produce clear feedback or a usable fallback. |
| In-place update, when there is a supported predecessor | Cover the previous and earliest supported versions and every distinct migration entry point. Install through the actual delivery path. Check identity, core content, references and pending state on first launch and a second cold start. Run populated fixtures for other supported versions. |
| Interruption during migration | Inject failure or kill the process before commit, between store commits and before post-commit cleanup. The next launch resumes or rolls back. Repeated launches preserve committed data and avoid duplicate records. |
| Older app opens newer data | Test newer primary with older recovery copy, and corrupt or missing primary with newer recovery copy. Startup, direct writes and delayed saves preserve bytes in the unsupported format. |
| Restore or device transfer | Import into a clean environment and reopen. Check identity, content, media references and pending items against the documented scope. Exercise wrong passwords, missing device-bound keys and damaged backups. The original environment remains recoverable. |
| Shutdown, logout, switch and delete | Committed content covered by retention survives restart. Removed data stays removed after delayed tasks or journal recovery, and other accounts remain usable. |
| Uninstall, reinstall and OS backup restore | Check local data, restored content, retained credentials and sign-in state against the product promise. A new install opens the correct initial state and restored data belongs to the correct owner. |
| Reconnect with an offline backlog | Use two real peers to exercise applicable direct or group messages, cancellation, retries, duplicate acknowledgements and network changes. Delivery state matches protocol guarantees. |

Bind each result to the **source revision, build versions and hashes (both artifacts for updates), actual delivery path, OS and device, fixture and data format versions, steps, expected and observed assertions, and relevant logs**. Record in-place updates, reinstall, cross-channel migration, same-version repair and system restore as distinct cases. Block the affected release if a core path loses identity or committed content, mixes accounts, leaks secrets, sends restored content without authorization or leaves startup unrecoverable. Applicable cases awaiting evidence stay `to do` or `needs device`. [X6 release evidence](testing.md#x6-packaged-release-verification--p0-for-release)

## Worked examples

| App | Business data and risks to exercise with an installed release |
|---|---|
| toxee | Use password-protected and unprotected accounts, two distinct identities, a legacy layout and a `.tox` import. After upgrade, check the same Tox public key, contacts, chats, pending or failed messages, and avatars. Check received files in the app data directory and the scope promised by full backup. Interrupt a password change or restore, then reopen the original account and verify the defined replay policy for saved queue entries. [Accounts and sessions](https://github.com/agentx-icu/toxee/blob/007b2e189a9642e045ca65e211dabfddf40eb5fa/doc/reference/ACCOUNT_AND_SESSION.md) |
| DitMesh | Use real peers to verify identity, contacts, groups, text and optional keying rhythm, pending operations, training and linked recordings. Check that an in-place upgrade preserves retryable items. For encrypted backup restore, verify the audit's review-only behavior for restored pending items and check for unintended sends. Inject failures across file and secure-store commits and exercise an unavailable Linux keyring. [Persistence audit](https://github.com/agentx-icu/ditmesh/blob/4dfe6f6aadc877a699fa2cdb2a8c100f864c91e2/doc/testing/PERSISTENCE_AUDIT.md) |
| MorseCQ | For an account-free learning profile, check course progress, mistakes, review plans, QSO drafts, preferences, recordings and their index. Exercise future-format handling and a delayed checkpoint after clearing data. The architecture snapshot describes portable backup storage without a user-facing operation and with recordings excluded. If device transfer is promised, qualify the user-accessible recovery path and its recording coverage. [Offline learning architecture](https://github.com/agentx-icu/morsecq/blob/c3805e94ae3bff0ecfb2e50fa379592c0bca7296/doc/architecture/OFFLINE_LEARNING.md), [persistence audit](https://github.com/agentx-icu/morsecq/blob/fad7bd7563f90e91d6dd015aaf843f7f71f4bd44/doc/testing/PERSISTENCE_AUDIT.md) |
